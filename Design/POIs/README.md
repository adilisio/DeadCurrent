# POIs: Specs, Ownership, Handoffs

This folder holds the production contract for points of interest. Strategy and reasoning: `Design/content_production_strategy.md`. This file is the short, practical version.

| File | Use |
| --- | --- |
| `TEMPLATE.md` | Copy to `<poi_id>.md` before building anything. |
| `AGENT_HANDOFF_TEMPLATE.md` | The contract passed from one role to the next. |

## Rules

1. **One POI, one spec.** No spec, no build. A spec with a blank section is not ready. The spec, not the chat, is the source of truth for scope.
2. **Isolate content.** Content-specific work lives in its own file, folder, sublevel, or per-POI script. See "How ownership works" below for the structure that exists. `Lvl_Boathouse` is generated by one script; the Landing Stage shows the per-POI pattern (its own script, one hook).
3. **Explicit ownership.** Every agent handoff lists the files it may edit and the files it must not. Anything unlisted is not owned.
4. **Shared foundations are integration-sensitive.** These change only through the Verifier / Integrator or a Systems Engineer handoff:
   - `Source/**`, especially rules, save, and world state
   - the shared generated-map scripts (`build_boathouse.py`, `build_test_gym.py`)
   - the generator cores `create_items.py`, `create_quest.py`, `create_dialogue.py` and the spec loader `content_specs.py` (the content itself is per file; see below)
   - `Tools/*.bat` (`RebuildContent`, `RunTests`, `ReviewCapture`, `Package`, `PlayTest`, `Maps`), `Config/*`
   - `Design/POIs/sombre_ids.md` (Phase 6 id ledger, created in VS-07), shared review entries, `Core/DCMapTestHelpers.h`
   - `Design/world_bible.md`, `CLAUDE.md`, phase plans
5. **One editor per generated file.** No two builders edit the same generated map script at the same time. Serialize, or split the content into separate files first. Content specs are already split one file per owner (see below).
6. **Persistent ids are immutable once accepted.** That covers actor ids, flags, quest stages, location ids, and saved asset names. Old saves must still load. A new POI adds ids; it does not rename shipped ones.
7. **Lore stays PROVISIONAL until Anthony confirms it.** List each provisional claim in the spec. Never explain the Current. Do not decide factions or Mara's backstory.
8. **A POI builder does not change global systems.** New content is layout, data, assets, dialogue, and tests. If the spec's "Missing Reusable Capability" is not empty, stop and hand off to a Systems Engineer with Anthony's approval.
9. **Builders do not approve their own work.** The Visual Critic, Gameplay Critic, and Verifier are separate passes, ideally separate agents. Only Anthony accepts.
10. **Use the tiers.** Tier A focal assets get Meshy or a hand-picked library asset. Tier B is the reusable kit. Tier C is dressing: no bespoke generation, NoCollision by default, exclusion zones honored.
11. **Log spend and provenance the same day.** Meshy credits, source paths, and licenses go in `Design/art_pipeline.md`.
12. **Keep the checklist current.** Every handoff ends with an update to `Design/ANTHONY_CHECKLIST.md`.

## Workflow

Spec (World Architect) → Build (POI, Narrative, Presentation Builders) → Review (Visual Critic, Gameplay Critic) → Revise (the original builder or a focused reviser) → Verify (Verifier / Integrator: rebuild, full suite, captures, package, smoke) → Anthony accepts.

Only accepted content becomes the baseline for the next POI.

## How ownership works (Phase 6, from VS-02)

What exists now, and who owns it. Anything not listed here is the Integrator's.

| Kind of file | Where | Owner |
| --- | --- | --- |
| **Content specs**: items, quests, dialogue | `Tools/ContentSpecs/{items,quests,dialogue}/<area>.py`, one file per owner (contract: `Tools/ContentSpecs/README.md`). The accepted Shore content is `items/shore.py`, `quests/shore_watch.py`, `dialogue/mara_intro.py`. | the builder who creates the file; the accepted Shore files are the Integrator's |
| **Generator cores** | `create_items.py`, `create_quest.py`, `create_dialogue.py`, `content_specs.py` | Integrator |
| **Per-POI map scripts** | one script per POI, called from the shared map script through one hook: the Landing Stage is the working example (`build_landing_stage.py`, hook `build_landing_stage_poi` in `build_boathouse.py`). Pointe Sombre's core script and its per-cell hooks arrive in VS-04 (plan §5.6). | the POI's builder; the hook and the core script are the Integrator's |
| **Per-cell review views** | `Tools/Review/<map>.json` plus `Tools/Review/<map>/<cell>.json`, merged by the capture (ids unique, exactly one route) | the cell's builder owns its file |
| **Per-cell map tests** | one new file per cell, `Source/DeadCurrent/Save/DC<Map><Cell>MapTest.cpp`, built on `Core/DCMapTestHelpers.h`; test names `DeadCurrent.Map.<Group>.<Test>`, where the group is the map's group in `Tools/Maps.bat` | the cell's builder (a test file is the only `Source/**` a POI builder creates) |
| **Generated `.umap` files** | `Content/Maps/*.umap` | **build products of the map scripts.** A builder commits scripts and data, not regenerated maps; the Integrator regenerates and commits the maps after merging. Only the Integrator commits a map. |
| **Content folders and art sublevels** | `Content/World/<Area>/<Cell>/`; one art sublevel per owner | the cell's builder |

**Integrator-owned shared files** (rule 4): `Source/**` outside a Systems Engineer handoff, the shared map scripts and their hooks, the generator cores, `Tools/*.bat` and `Config/*`, the id ledger, phase plans and `CLAUDE.md`, `Core/DCMapTestHelpers.h`, and the generated maps.

**Machine workflow.** `Tools\RunTests.bat [-build] [Map.<Group>]`, `Tools\ReviewCapture.bat [map]`, `Tools\Package.bat`, `Tools\PlayTest.bat [map]` all take the maps registered in `Tools/Maps.bat` (one line per map). `Tools\DumpContent.bat <label>` proves a content-generator change kept the accepted content.

## Branches and worktrees for parallel agents

Two agents must never share one working tree: the editor holds locks, builds write `Binaries` and `Intermediate`, and content scripts write `Content`. Each active builder gets a branch and its own worktree:

```
git fetch origin
git worktree add C:\DeadCurrent_wt\<package> -b vs/<package> <starting commit>
cd C:\DeadCurrent_wt\<package>
```

- The first build in a new worktree is a full C++ build (about as long as a clean clone); `Tools\RunTests.bat -build` does it.
- **Commit** on your own branch `vs/<package>`; **push** only that branch (`git push origin vs/<package>`). Never push `main`, merge into `main`, rebase a shared branch, or force-push.
- The Integrator merges one package at a time into `main` with `--no-ff`, regenerates the maps, runs the full suite, and pushes `main`.
- Stay inside the handoff's owned files. Do not sweep another owner's uncommitted edits into a commit; check `git status` first.
- Close the editor before running any `Tools\*.bat` that launches the engine, and do not run two engine-launching tools at once from the same worktree.
- Remove a finished worktree with `git worktree remove C:\DeadCurrent_wt\<package>` after the Integrator has merged it.

## Before parallel work starts

- Confirm the files each agent owns do not overlap.
- Confirm the baseline commit and test count in every handoff.
- Prefer one branch or worktree per owner. Integrate in small batches and rerun the full suite after each.
- The first parallel wave (Phase 6) is prepared in `Design/POIs/handoffs/PHASE6_WAVE1.md`.
